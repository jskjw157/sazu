# 상용 사주 앱의 원천 데이터·오픈소스·API 선정 조사

조사일: 2026-10-20  
대상: AI 연애 파트너 안에서 사주·궁합·운세를 제공하는 한국어 모바일 웹 앱  
문서 상태: 도입 의사결정을 위한 조사·제안. 상용 엔진 검수 완료나 API 계약 완료를 의미하지 않는다.

## 1. 권장 결정

**현재 프로젝트에는 “공식 한국 달력 자료 + 버전을 고정한 천문 계산 + 직접 관리하는 사주 규칙 + 자체 해석 콘텐츠” 구성이 가장 적절하다.** 외부 유료 API는 개발 기간을 줄이는 대안이지만, API라는 전달 방식이 정확성을 보장하지 않는다.

우선순위는 다음과 같다.

| 용도 | 1차 후보 | 도입 조건 |
|---|---|---|
| 한국 양력↔음력·윤달 | KASI 음양력 API를 기준으로 검증한 usingsky/korean_lunar_calendar 또는 허용된 공식 응답 적재 | 지원기간·윤달·왕복 변환을 확인하고 코드 및 데이터 출처 기록 |
| 절입 시각 | Skyfield + JPL 천문력으로 생성하고 KASI 공식 값과 비교 | 천문력·시간 모델 버전 고정, 출시 지원기간 전체 검증 |
| 공식 절기 기준값 | KASI 1920–2100년 24기 TXT | 상용 DB 저장·가공 조건은 별도 확인 |
| 출생 당시 시간 | IANA tzdb | 당시 표준시·DST를 적용하고 버전 저장 |
| 연주·월주·일주·시주·대운 | 앱의 명시적인 ruleset | 달력 간지와 사주 간지를 구분하고 선택한 관습을 고정 |
| 연애 해석·파트너 문장 | 자체 작성·검수한 콘텐츠 + LLM | 계산 근거·콘텐츠 버전 연결. 생성 문장을 역법 원천으로 재사용하지 않음 |
| 외부 API 대안 | SAZU·운세위키를 실제 입력 PoC 후보로 검토 | 상용 권리·저장·AI 재가공·시간 규칙 확인 후 비교 |

**지금 바로 무검증 상태로 채택하라는 추천은 아니다.** 아래 연구로 가장 유망한 구성과 보류할 후보를 좁혔다. 실제 출시 승인은 지원기간과 규칙을 고정한 다음 검증해야 한다.

### 앞선 자료의 보완

이전 검토에서 월력요항의 공개 범위만 보고 1990년대 절기 원천이 미확보로 남았다면 그 판단은 수정해야 한다. KASI 역서 페이지에는 **1920–2100년 절기 시각 TXT의 실제 다운로드 링크**가 있으며, 이번에 파일을 내려받아 확인했다. 다만 자료 확보와 상용 이용권 확인은 별개다. [S01][S04]

## 2. “정확한 사주 데이터”를 세 층으로 구분해야 한다

| 층 | 검증할 내용 | 검증 방법 |
|---|---|---|
| 천문·역법 | 양음력 날짜, 윤달, 절입 순간, 시간대 | 공식 달력과 수치 비교, 천문력 교차 계산, 경계값 시험 |
| 명리 계산 규칙 | 입춘 연주, 12절 월주, 자시 일주, 시주·대운 정책 | 채택한 규칙과 코드가 일치하는지 확인 |
| 해석 콘텐츠 | 성격·관계·연애운에 대한 문장 | 원문 근거, 일관성, 사용자 경험, 과도한 단정 여부 평가 |

앞의 두 층에서 숫자가 일관되게 나온다는 사실이 연애 결과나 미래 예측의 타당성을 증명하지는 않는다. 이번 조사는 소프트웨어가 선택한 달력·계산 규칙을 재현하는지에 관한 것이다.

“한국천문연구원 데이터를 쓴다”는 말도 범위를 좁혀야 한다. KASI의 음양력·천문 자료는 역법의 원천이며, 개인의 연애운 해석·궁합 점수·용신 판정까지 공식 인증하는 데이터가 아니다. [S02][S03]

## 3. 공식 원천: KASI를 어떻게 사용할 것인가

### 3.1 음양력 API

- 공식 페이지: https://www.data.go.kr/data/15012679/openapi.do
- 기본 조회: `LrsrCldInfoService/getLunCalInfo`
- 제공 항목: 양력·음력 연월일, 평달/윤달, 요일, 율리우스적일, 역일 간지 등.
- 공식 조건: 무료, 이용허락범위 제한 없음, 개발·운영 자동승인.
- 개발계정 트래픽은 10,000으로 표기하며, 운영 증설 신청을 안내한다. 포털에 단위가 명확하지 않은 항목을 임의의 SLA로 바꾸지 않는다.
- 공식 시간범위 항목은 “-”이다. 특정 오픈소스의 지원기간을 API의 보장 범위로 옮기면 안 된다. [S02]

`solDay`는 선택 항목이다. 월별로 응답을 받아 적재하는 방식을 검토할 수 있지만, 실제 반환 개수·페이지 처리·지원기간은 인증 응답으로 확인해야 한다. 이번에는 사용자 계정이나 인증키를 발급·사용하지 않아 실제 성공 응답·지연은 측정하지 않았다.

**권장 사용:** 로컬 한국 달력의 검증 기준 또는 이용조건에 맞춘 배치 적재 원천. 사용자 채팅 한 번마다 의존하도록 설계할 필요는 없다.

주의할 점은 `lunSecha`·`lunWolgeon`이 이름만으로 앱의 연주·월주가 되지는 않는다는 것이다. 입춘·절입을 사용하는 앱의 정책과 의미가 일치하는지 별도 시험해야 한다.

### 3.2 1920–2100년 24기 TXT — 실제 파일 확인

- 출처 페이지: https://astro.kasi.re.kr/kor/almanac/pageView/26
- 직접 다운로드: https://astro.kasi.re.kr/kor/almanac/solarTerms/download

실제 파일 파싱 결과는 다음과 같다. 이는 구조 확인이며 전체 천문 계산의 독립 검산은 아니다.

| 항목 | 확인한 값 |
|---|---|
| 기간 | 1920–2100년 |
| 행 수 | 4,344 = 181년 × 24기 |
| 연도별 개수 / 키 중복 | 매년 24개 / 연도·절기 키 중복 0 |
| 원문 시계 | 고정 UTC+9 |
| 원문 정밀도 | 분 단위 반올림 |
| 날짜 경계 | 반올림으로 자정을 넘으면 원래 날짜의 24:00 |
| 헤더 날짜 | 2026-09-01 |
| 파일 해시 | SHA-256 508761248c7d18eb1ca1bcb1fcace2ba29f3f511d085321ae1e633c74d8e9e34 |

원문은 과거 표준자오선 변경·서머타임을 반영하지 않는다고 설명한다. 따라서 파일의 UTC+9를 과거 Asia/Seoul 현지시각으로 다시 해석하면 오히려 시간축이 어긋난다. 출생기록의 당시 시계와 절기 원문의 시계는 각각 UTC로 정규화해서 비교한다.

24:00 표기는 실제로 세 건 있었다. 파서는 원문 날짜·시각을 보존하면서 다음 날 00:00을 정규화 값으로 별도 저장해야 한다. 미래 값은 지구 자전 예측 등의 변화로 수정될 수 있으므로 원천 버전을 보존한다. [S01][S05]

### 3.3 특일 API의 절기 기능

https://www.data.go.kr/data/15012690/openapi.do

공식 설명에 24절기 조회가 포함되어 있고, 무료·이용허락범위 제한 없음으로 표시된다. 다만 공개 페이지 기본 상세표는 기념일 조회인 `getAnniversaryInfo`였다. 그 표에 시각 필드가 없다는 이유로 24절기 기능도 시각을 제공하지 않는다고 단정하면 안 된다. [S03]

최신 v1.4 기술문서 파일명은 확인했으나 공식 첨부 본문을 확보하지 못했고, 현재 인증 API 응답도 확인하지 않았다. 따라서 `get24DivisionsInfo`의 실제 시각 필드·지원기간은 도입 시 확인할 항목이다. 공식 TXT의 존재는 별도로 확인했으므로 이 미확인이 과거 절기 원천 전체의 부재를 의미하지 않는다.

### 3.4 API와 TXT의 이용권은 별개

KASI 저작권정책은 공공누리 제1유형 표시 자료의 출처 표시 이용을 안내하고, 표시가 없는 자료는 담당자와 사전 협의하도록 적고 있다. 이번에 TXT의 개별 이용표시를 확인하지 못했다. [S04]

따라서 공공데이터포털 API의 “이용허락범위 제한 없음”을 별도 TXT·역서 스캔 이미지에 자동 적용하지 않는다. 실서비스 DB 저장·가공·배포 범위를 확인하거나, 이용조건이 명확한 원천과 자체 계산 결과를 사용한다. 이 보고서에는 원본 TXT 전체를 재배포하지 않고 출처와 조사 결과를 기록했다.

MIT/BSD 코드는 보통 폐쇄형 상용 서비스에 적용할 수 있는 조건을 제공하지만, 저작권·라이선스 고지 등을 지켜야 한다. 저장소의 라이선스와 포함 데이터·외부 콘텐츠의 권리 관계도 기록해야 한다. “GitHub 공개” 자체를 허가로 해석하면 안 된다. 각 후보의 실제 라이선스 원문은 출처 목록에 연결했다. [S06–S19]

### 4.2 usingsky/korean_lunar_calendar

공식 저장소: https://github.com/usingsky/korean_lunar_calendar_py  
시험한 소스: 0.4.0, commit `128a9b482dd34ea6185298d335de2c8d3f378d4c`.

한국 음양력 변환 테이블을 내장해 오프라인으로 실행한다. 공식 기관이 배포하는 라이브러리 자체는 아니며, 제작자가 한국천문연구원 기준을 따른다고 설명하는 제3자 구현이다. 지원 범위는 양력 1000-02-13~2050-12-31, 음력 1000-01-01~2050-11-18로 명시된다. 범위와 변환 성공 여부를 확인한 후 결과를 읽어야 한다. [S06]

**잘 맞는 용도:** 한국식 음력 생일을 양력으로 바꾸기, 윤달 여부 확인, 오프라인 달력 적재.

**부족한 부분:** 절입 순간에 따른 연주·월주, 지역·역사적 시각, 선택한 자시 규칙, 대운·격국·용신 등. `getGapJaString`을 호출했다고 이 부분이 모두 해결되는 것은 아니다.

이번에 중국 라이브러리와 실제 비교했다.

| 양력 입력 | usingsky 결과 | 6tail 결과 |
|---|---|---|
| 2017-06-24 | 음력 2017 윤5월 1일 | 음력 2017 평6월 1일 |
| 2017-07-23 | 음력 2017 평6월 1일 | 음력 2017 윤6월 1일 |

이 시험은 두 라이브러리의 차이를 재현한 것이며, 자체로 전체 한국 역법 검증은 아니다. 다만 한국·중국 음력을 그대로 교체할 수 없다는 구체적인 근거가 된다. 같은 두 라이브러리가 일치한 2023-03-22, 2026-02-17도 확인했다. 일부 정상 예제만으로 두 역법이 같다고 판단해서는 안 된다.

### 4.3 Skyfield + JPL 천문력

공식 문서: https://rhodesmill.org/skyfield/almanac.html  
라이선스: https://github.com/skyfielders/python-skyfield/blob/master/LICENSE

Skyfield는 계산 라이브러리이고 JPL kernel은 천체 위치 계산의 입력 데이터다. 둘을 합쳐 태양 황경의 절입 순간을 구할 수 있다. Skyfield에는 24절기 계산 함수가 문서화되어 있다. [S08][S09]

시험 구성은 **Skyfield 1.55 + DE440s**이다. DE440s의 문서상 범위는 약 1849–2150년이다. 실제 사용 범위는 kernel 안의 구간도 검사해야 한다. 공식 배포처에는 DE442 계열도 존재하므로 DE440을 “가장 최신”이라고 부르지 않는다. 이번에는 재현 가능한 비교를 위해 버전을 고정했다. [S10][S11]

JPL/NAIF의 kernel 이용조건과 Skyfield MIT 조건은 다르다. NAIF 공식 안내는 공개 kernel 이용·원형 재배포와 상업적 사용 등에 관한 조건을 설명한다. 이를 뭉뚱그려 “JPL 데이터도 MIT”라고 기록하면 안 된다. [S12]

**권장 방식:** Python으로 절기 시각을 배치 생성해 검증한 뒤 JSON 또는 SQL로 저장하고, 실제 앱의 Node/TypeScript 서버는 이 테이블을 조회한다. 사용자의 모든 채팅 요청을 Python 천문 계산이나 외부 API에 연결할 필요는 없다.

Skyfield 자체는 완성된 한국 음력 변환기나 사주 풀이 엔진이 아니다. 달력·명리 규칙은 별도다.

### 4.4 Astronomy Engine

공식 저장소: https://github.com/cosinekitty/astronomy  
시험 버전: Python astronomy-engine 2.1.19.

**해석의 한계는 다음과 같다.**

3. 몇십 초의 차이로 분 반올림 결과가 갈릴 수 있다. 일치 건수만으로 천문 엔진의 전반 품질을 평가하지 않는다.
4. 전체 1920–2100년, 음양력 변환, 원국·대운, 해외 출생·과거 DST를 검증한 결과는 아니다.

Core PAYG 90원, Professional 150원, Core Starter 월 30,000원/500건 등의 가격은 12월 적용 예정이다. VAT 별도이며 현재 바로 구매 가능한 신규 요금제로 오해하면 안 된다. API 공개 문서의 범위와 실제 발급 키·계약·SLA 범위도 구분한다. [S30]

### 6.4 UN7

https://un7.kr/  
https://un7.kr/doc/

공개 명세는 제목·설명 중심의 완성 운세 문구를 반환한다. 원국 네 기둥과 절입 비교 과정을 투명하게 제공하는 백엔드와 역할이 다르다. 문서 갱신 표시는 2016-09-29이고, 공개 테스트 키는 실제 계산값이 아닌 파라미터 확인용이라고 명시한다. 서비스 중단을 단정할 근거는 없지만 실제 운영·지원 상태는 확인해야 한다. [S31][S32]

저렴한 배너용 일간 콘텐츠가 필요할 때 검토할 수 있다. 이 상품의 단가와 원국 계산·심화 분석 API의 단가를 바로 비교하지 않는다.

## 7. API를 호출하면 더 정확한가

**같은 원천과 규칙을 같은 버전으로 구현했다면, API 호출과 로컬 계산이라는 차이만으로 결과가 달라질 이유는 없다.** 실질적인 차이는 공급자가 어떤 검증·업데이트·운영 책임을 맡는지다.

| 판단 기준 | 자체 계산 | 외부 계산 API |
|---|---|---|
| 원천·규칙 확인 | 코드·데이터까지 확인 가능 | 공개 필드·문서·계약에 의존 |
| 초기 작업 | 구현·검증 부담이 큼 | 문서가 맞으면 연동을 줄일 수 있음 |
| 결과 재현 | 버전·입력을 보관하면 통제하기 쉬움 | 공급자 버전 고정·변경 통지 필요 |
| 호출 비용 | 운영·유지보수 비용 | 호출료·최소 구독·재시도 과금 |
| 장애 영향 | 자체 서비스 운영 문제 | 외부 장애·한도·서비스 종료 영향 추가 |
| 사용자 입력 | 자체 환경에서 처리 가능 | 외부 처리·보관 범위 확인 필요 |
| 교체 가능성 | 원천과 인터페이스를 분리하면 높음 | 스키마·이용권·기존 결과의 권리 확인 필요 |

실제 API가 유리한 경우는 계산·명리 검수 인력을 확보하기 어렵고, 공급자가 채택한 규칙이 앱의 정책과 맞으며, 실데이터 경계 시험과 상용 계약을 통과한 경우다. API를 사면 검증 업무가 완전히 사라지는 것은 아니다.

반대로 사용자별 원국은 출생 입력·ruleset·계산 엔진·원천 데이터 버전이 모두 같으면 재사용할 수 있다. 허용된 캐시·삭제 정책 아래 저장하고, 대화마다 계산을 다시 호출하지 않는다. 세운·월운·일운은 대상 날짜·시각·규칙 버전을 키에 포함하는 별도 계산이다. LLM 문장 생성과 원국 재계산의 비용도 나눠 측정한다.

## 8. 프로젝트에서 만들 DB의 구체적 형태

대량의 “생년월일별 연애운 문장”을 먼저 수집하기보다 재현 가능한 원천과 계산 규칙을 먼저 만든다. 다음은 제안 스키마이며 현재 구현되어 있다는 뜻은 아니다.

| 자료 묶음 | 주요 필드 | 목적 |
|---|---|---|
| source_registry | source_id, url, fetched_at, version, sha256, license_url, commercial_use_status, supported_range | 출처·권리·버전 추적 |
| calendar_day | calendar_system, solar_date, lunar_year/month/day, is_leap_month, source_id, dataset_version | 한국 음양력 변환 |
| solar_term | term_code, target_longitude, raw_local_value, source_clock, precision, event_utc, ephemeris_version, timescale_version | 연도별 절입 순간 |
| ruleset | year_boundary, month_boundary, day_rollover, hour_rule, solar_time_mode, daeun_rule, version | 명리 정책을 명시 |
| calculation_result | subject_id, normalized_input, uncertainty, pillars, features, source_versions, engine_version, ruleset_version | 결과 재현·원인 설명 |
| interpretation_content | feature_condition, topic, source_note, author, reviewer, approved_version | 자체 해석 콘텐츠 |
| reading | calculation_id, content_version, model_version, prompt_version, rendered_text | 계산 결과와 캐릭터 설명 연결 |

### 데이터 처리에서 빠지면 안 되는 점

1. **한국 달력의 날짜 의미를 보존한다.** 음력 입력은 달력 체계와 윤달 여부를 반드시 함께 받는다. 해외 출생자가 “한국 음력 생일”을 입력하면 출생지의 날짜와 어떻게 연결할지 정책을 정의한다.
2. **출생시각과 절기 시각을 공통 시간축으로 비교한다.** 출생 당시 현지 표준시·DST에는 tzdb를 사용한다. KASI TXT에는 고정 UTC+9 변환을 적용한다. IANA 자료에는 한국의 과거 30분 표준시와 DST 이력이 들어 있다. [S33]
3. **진태양시는 명리 선택이다.** 지역·균시차 보정의 천문학적 정의와 이를 사주에 적용할지는 구분한다. 기본값을 하나 정하고 응답에 기록한다.
4. **시간 미상에 정오를 몰래 넣지 않는다.** 시주 없음 또는 가능한 범위로 표현한다. 입춘·절입 당일의 시간 미상은 연·월주도 여러 후보가 될 수 있다.
5. **정밀도를 거짓으로 높이지 않는다.** 분 반올림 자료의 05:02를 “정확히 05:02:00”으로 확정하지 않는다. 약 30초 경계 구간은 더 정밀한 원천 또는 불확실성 처리가 필요하다.
6. **같은 이름의 절기를 서로 다른 인덱스로 섞지 않는다.** KASI 코드·천문 라이브러리의 황경 인덱스·앱의 월 순번을 명시적으로 매핑한다. 이번 비교도 이 매핑을 따로 수행했다.
7. **기존 결과를 조용히 덮어쓰지 않는다.** 원천·규칙 변경을 새 버전으로 만들고 영향받는 리딩을 식별한다. 사용자의 출생정보 수정·삭제는 이에 맞게 반영한다.

초기 지원 범위를 예를 들어 1920–2050년으로 정하면 공식 TXT와 usingsky의 현대 날짜 범위가 겹친다. 단, 1월 초의 이전 절기와 대운 계산에 필요한 다음 절기 등 **조회 경계 바깥의 보조 구간**도 확보해야 한다. 자료가 존재한다는 사실과 그 기간이 검수되었다는 사실은 구분한다. 현재 성인 타깃이므로 미래 출생자를 가입 대상으로 받는다는 뜻도 아니다.

분 단위 원천만 사용할 때는 경계 바로 ±1초를 참값 시험으로 삼을 수 없다. 정밀한 엔진의 정책 시험과 반올림 공식 자료 대조를 분리하고, 각 근거의 정밀도에 맞는 입력을 선택한다.

복수 엔진의 다수결도 정답을 대신하지 못한다. 같은 원천을 공유하는 구현인지, 한국·중국 달력 차이인지, 명리 관습 차이인지, 실제 코드 오류인지 분류해야 한다.

## 10. API 업체에 받을 답변 — 문의 초안

문의는 실행하지 않았다. 실제 구매 후보에게 다음을 구체적으로 확인하면 된다.

1. 양음력·절입 데이터의 출처와 버전, 지원 연도, 출력 시각의 시간대·정밀도는 무엇인가?
2. 입춘 연주·12절 월주·자시·야자시·진태양시·대운 규칙을 어떤 식별자로 반환하는가?
3. 한국 과거 표준시·DST, 해외 출생과 알 수 없는 도시를 어떻게 처리하는가?
4. 고정 샘플이 아닌 실제 임의 출생 입력을 계산하는 시험 환경을 제공하는가?
5. 우리 앱의 유료 사주·궁합·AI 연애 파트너 기능이 계약상 허용되는가? 경쟁 서비스 조항과 별도 API 계약의 관계는 무엇인가?
6. 결과 저장·캐시·장기 표시·서비스 이전·계약 종료 후 기존 고객 리딩 제공은 어디까지 허용되는가?
7. 외부 LLM 입력, 새 문장 생성·판매, 검색 임베딩, 모델 학습을 각각 허용하는가?
8. 원천 라이선스가 최종 앱과 B2B API 고객까지 허용하는가? Swiss Ephemeris를 사용한다면 우리에게 추가 라이선스가 필요한가?
9. 입력 로그 무보관·사용자별 삭제·보관 기간·수탁사·처리 지역을 명시할 수 있는가?
10. 버전 고정·사전 변경 통지·재시도 중복 과금 방지·장애 보상·종료 통지·반출을 계약에 넣을 수 있는가?

## 11. 실행 순서 제안

**1단계: 계산 범위를 한 장으로 확정한다.** 한국 양음력, 출시 지원연도, 출생시각 미상 처리, 자시·태양시·대운 규칙을 먼저 결정한다.

**2단계: 원천을 버전별로 확보한다.** KASI API 지원범위·사용 조건을 확인하고 한국 달력을 검증한다. Skyfield/JPL로 절기 후보를 만들고 공식 자료와 대조한다. 별도 TXT의 상용 복제 조건을 확인한다.

**3단계: 경계 검증을 통과한 자체 계산 API를 만든다.** 내부 계산 방식과 외부 노출 인터페이스를 분리하여 원천을 바꾸더라도 앱 화면·결제·대화가 흔들리지 않게 한다.

**4단계: 자체 해석 콘텐츠를 연결한다.** 계산 특징→검수 문장→캐릭터 개인화 순서로 연결한다. 유튜브 자막·타사 운세 문장을 대량 복사해 원천 DB로 채우지 않는다. 사주 원국의 오행 수, 해석 점수, 사용자 감정 추정도 서로 다른 필드로 관리한다.

**5단계: 외부 API를 비교 기준 또는 대체 공급자로 평가한다.** SAZU·운세위키가 권리와 실제 입력 시험 조건을 충족하면 같은 검증 세트로 평가한다. Ablecity는 신규 상용 이용 가능일 이후에 다시 검토한다.

빠른 출시를 위해 API를 선택하더라도 source_registry와 ruleset, 결과 버전 추적은 유지한다. 현재 자료만으로 특정 유명 상용앱의 내부 DB나 공급자를 추정하지 않는다.
